# UC-SYS-10 — Thiết lập mật khẩu tài khoản được mời

| Thuộc tính | Nội dung đặc tả |
|---|---|
| Mã Use Case | UC-SYS-10 |
| Tên Use Case | Thiết lập mật khẩu tài khoản được mời |
| Mô tả nghiệp vụ | Người nhận lời mời tài khoản do quản trị tạo đặt mật khẩu để sử dụng User đã có. Luồng không tạo User mới, không nhận StaffInvite/TenantInvite, không tự cấp phiên. Cơ chế redeem trùng kỹ thuật với UC-SYS-06 nhưng mục tiêu là thiết lập password tài khoản được mời [ORIGIN, SVC]. |
| Phạm vi và cấp độ | Hệ thống quản lý nhà trọ; G01 — Tài khoản và an toàn truy cập; mục tiêu người dùng, AS-IS. |
| Tác nhân chính | Khách/chưa đăng nhập (A01) |
| Tác nhân phối hợp | Không áp dụng |
| Mục tiêu nghiệp vụ | Đặt mật khẩu bằng liên kết mời một lần rồi đăng nhập; không tự chọn vai trò hoặc cấp quyền mới. |
| Sự kiện kích hoạt | A01 mở liên kết /account/activate#token=... đã nhận trước đó hoặc nhập token trên màn hình Đặt mật khẩu tài khoản [UI, LINK]. |
| Tiền điều kiện | Trong ngữ cảnh này User đã được admin tạo với passwordHash ngẫu nhiên không cung cấp cho người nhận và token purpose INVITE đã được enqueue. AdminInviteDto chỉ cho role LANDLORD hoặc ADMIN; không suy diễn cùng API mời tạo STAFF/TENANT. Để redeem cần User active, token khớp hash/chưa dùng/chưa hết hạn. Backend redeem không thực sự kiểm purpose INVITE hoặc role; đây là ngữ cảnh UC, không phải điều kiện kỹ thuật bổ sung [ORIGIN, ORIGIN-VAL, SVC]. Không cần JWT, không cần delivery.ready khi đổi token đã có. |
| Dữ liệu đầu vào và Validation | token bắt buộc string 32–128; parser URI chấp nhận fragment trước query, chỉ base64url 32–128; form nhập tay chỉ kiểm min32, DTO không regex charset. password Chuỗi 12–128 ký tự, có ít nhất một chữ hoa A–Z, chữ thường a–z, chữ số 0–9 và ký tự ngoài A–Za–z0–9; không có kiểm tra lịch sử mật khẩu hoặc cấm trùng mật khẩu cũ [VAL].<br>confirm password chỉ UI, phải trùng; không có trường chọn email/userId/role. User đích xác định từ token, không theo tài khoản cục bộ đang đăng nhập [UI, LINK, VAL, SVC]. |
| Luồng thành công chính | B1 — A01 mở /account/activate với token từ fragment/query; UI nạp token vào trường mã che nội dung, hoặc người dùng nhập mã có sẵn [LINK, UI].<br>B2 — A01 nhập mật khẩu mới và xác nhận, chọn Đặt mật khẩu; UI validate, busy=true, POST /api/v1/auth/account-access/redeem {token,password} [UI, API].<br>B3 — Backend áp DTO/limiter 5/60 giây và băm password argon2. Trong transaction, tìm AccountAccessToken theo SHA-256, khóa User rồi đọc lại token/User; kiểm token chưa dùng/hạn còn/User active [CTRL, SVC].<br>B4 — Hệ thống consume token với điều kiện consumedAt=null/count=1; thay passwordHash của User đã có, tăng sessionVersion; thu hồi mọi refresh token, consume mọi account token chưa dùng và cancel mọi job token user còn PENDING/PROCESSING, xóa payload/lease [SVC, DB].<br>B5 — Hệ thống ghi audit auth.access_token_redeemed trong cùng transaction rồi commit; trả data {signInAgain:true} [SVC].<br>B6 — UI gọi SessionController.logout để dọn phiên cục bộ nếu có, done=true, xóa token/password/confirm khỏi form và hiển thị Mật khẩu đã được cập nhật. Vui lòng đăng nhập lại. [UI, STATE, STORE].<br>B7 — A01 chọn Đăng nhập để tới /auth/login; đăng nhập và MFA nếu cần thuộc mục tiêu sau, không tự phát JWT từ redeem [UI]. |
| Luồng thay thế | A1 — Tại B1, link thiếu/sai token parser trả null: UI vẫn cho nhập Mã từ liên kết; nhập token đã có hợp lệ rồi quay B2; chưa có request redeem/ghi DB [UI, LINK].<br>A2 — Tại B1/B2, người dùng chọn Yêu cầu liên kết khôi phục mới: UI mở PasswordRecoveryDialog, chuyển ngữ cảnh sang UC-SYS-06. Không phải nút gửi lại INVITE, không tạo User mới; dữ liệu hiện tại không đổi chỉ vì mở dialog [UI, RECOVERY].<br>A3 — Tại B3, token hợp lệ có purpose PASSWORD_RESET hoặc chuỗi purpose khác thay vì INVITE: service vẫn redeem vì không có ràng buộc purpose. Đi tiếp B4–B7, cùng thay password user token; ghi nhận tái sử dụng kỹ thuật, không tạo quyền/phân nhánh giả [SVC]. |
| Luồng ngoại lệ | E1 — Tại B2, mã quá ngắn/password không policy/confirm lệch: UI lỗi field và không gửi; sửa B2. Gọi trực tiếp sai DTO/unknown field: 400 VALIDATION_ERROR, chưa service. UI redeem không trình bày details mà thông báo chung ở E4 [UI, CTRL, HTTP, ERR].<br>E2 — Tại B3, vượt limiter 5/60 giây: 429 RATE_LIMITED, không ghi; UI thông báo chung, busy=false; kết thúc lần gửi [CTRL, ERR, UI].<br>E3 — Tại B3, token không có/đã dùng/expired hoặc User inactive: 401 UNAUTHORIZED Link không hợp lệ hoặc đã hết hạn.; hoặc consume count khác 1 tại B4: 409 CONFLICT; transaction không commit password/version/token/job/audit. UI thông báo chung, cho mở yêu cầu link khôi phục mới nhưng không tự gửi [SVC, UI].<br>E4 — Tại B3–B6, lỗi DB/mạng/parse/logout đều vào catch UI: Liên kết không hợp lệ, hết hạn, đã dùng hoặc dịch vụ chưa khả dụng. Bạn có thể yêu cầu liên kết khôi phục mới.; busy=false, done chưa bật. Nếu backend đã commit thì password mới và token consumed vẫn còn; mất response không bảo đảm chưa kích hoạt. Lỗi DB trong transaction mới có bảo đảm không commit nhóm ghi, không mở rộng sang logout/storage [UI, SVC, STORE, ERR]. |
| Hậu điều kiện thành công | Password User sẵn có thay đổi, User.id/role không đổi, sessionVersion tăng; refresh token revoked, account tokens chưa dùng consumed, job pending/processing cancel, audit redeem lưu. Không gán Tenant/StaffProfile hay permission mới trong redeem. Không phát access/refresh token; UI yêu cầu đăng nhập lại [SVC, UI]. |
| Bảo đảm tối thiểu khi thất bại | Trước commit redeem, nhóm password/version/token/job/audit nằm trong một transaction. User đã được tạo ở quy trình mời trước đó không bị xóa khi redeem thất bại. Sau commit, lỗi response/logout không trả password về giá trị cũ, không hoàn nguyên lời mời. Token đã consume không tái sử dụng [ORIGIN, SVC, UI]. |
| Quy tắc nghiệp vụ | BR-01 — Đây là User đã có; quy trình admin invite tạo LANDLORD/ADMIN và enqueue INVITE, khác accept Tenant/Staff tạo mới từ invite [ORIGIN, ORIGIN-VAL].<br>BR-02 — Token enqueue hạn 30 phút; redeem kiểm expiresAt/consumedAt/User active nhưng không kiểm purpose hay role, không kiểm delivery config [SVC].<br>BR-03 — Redeem thành công consume toàn bộ token chưa dùng của User, kể cả PASSWORD_RESET/INVITE khác; không giữ phiên hiện tại [SVC].<br>BR-04 — Không yêu cầu password cũ hoặc MFA trong redeem; nếu ADMIN cần MFA thì xử lý sau đăng nhập, không tự bật MFA từ liên kết [CTRL, SVC].<br>BR-05 — Trạng thái invitation lifecycle ADMIN dùng audit auth.access_token_redeemed để coi ACTIVATED; không chỉ dựa purpose token đã đổi. Heuristic này không có nhánh purpose riêng trong redeem, cần lưu ý khi đối chiếu nhãn kích hoạt [LIFECYCLE, SVC]. |
| Phân quyền và bảo mật | A01 người nắm token, không phải admin tạo lời mời. Endpoint public có DTO/limiter, hash token và lock User; không chọn đích từ email/body. Không bổ sung E01: quy trình redeem không gọi delivery provider; việc gửi lời mời thuộc UC quản trị trước đó. Nếu client đang có session khác, logout sau thành công dọn phiên client đó, không đổi đích password đã xác định qua token [UI, SVC, STORE]. |
| Kết quả đầu ra | POST mặc định 201 data {signInAgain:true}; không trả password, không User mới, không session. UI success yêu cầu đăng nhập lại; khi parser không có token vẫn form nhập tay [CTRL, UI]. |
| Quan hệ với Use Case khác | Giữ nguyên UC-SYS-10 và UC-SYS-06 do mục tiêu/trigger khác nhau, dù dùng chung RedeemDto/service/UI. Không include/extend giữa chúng. UC-SYS-08/09 dùng invite khác, tạo User rồi cấp phiên; không coi ba UC này là bản trùng đơn thuần [UML, SVC, ORIGIN]. |
