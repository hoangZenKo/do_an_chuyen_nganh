# UC-ADM-07.1 — Thiết lập MFA Admin

| Thuộc tính | Nội dung đặc tả |
|---|---|
| Mã Use Case | UC-ADM-07.1 |
| Tên Use Case | Thiết lập MFA Admin |
| Mô tả nghiệp vụ | Quản trị viên thiết lập secret TOTP, xác nhận bằng mã từ ứng dụng xác thực và nhận 8 mã khôi phục. Chỉ enrollment/confirmation thuộc UC này; login dùng MFA hoặc step-up thao tác nhạy cảm là ngữ cảnh khác [CTRL, MFA]. Mã UC giữ tiền tố ADM nhưng nằm G01 theo Catalog. |
| Phạm vi và cấp độ | Hệ thống quản lý nhà trọ; G01 — Tài khoản và an toàn truy cập; mục tiêu người dùng, AS-IS. |
| Tác nhân chính | Quản trị viên nền tảng (A05) |
| Tác nhân phối hợp | Không áp dụng |
| Mục tiêu nghiệp vụ | Tạo và xác nhận cấu hình MFA với mã khôi phục |
| Sự kiện kích hoạt | A05 mở Bảo mật admin (/admin/security); UI cũng điều hướng đến đây khi adminMfaRequired=true và phiên chưa verified [UI, NAV]. |
| Tiền điều kiện | JWT access hợp lệ; user.role=ADMIN và có AdminProfile được provision trước. MFA chưa bật để enroll/confirm. ADMIN_MFA_ENCRYPTION_KEY phải giải mã base64 đúng 32 byte để mã hóa/giải mã secret. Không yêu cầu đã MFA verified ở chính màn hình thiết lập [CTRL, MFA, JWT]. |
| Dữ liệu đầu vào và Validation | GET status và POST enroll không DTO body nghiệp vụ. confirm nhận code string bắt buộc 6–64 ký tự ở MfaCodeDto; UI chỉ submit khi trim.length=6; service kích hoạt chỉ nhận mã số 6 chữ số TOTP hợp lệ, không nhận recovery code để kích hoạt. secret sinh ngẫu nhiên 20 byte; URI otpauth chứa issuer=RentalRoom, algorithm=SHA1, digits=6, period=30 [CTRL, MFA, UI]. |
| Luồng thành công chính | B1 — A05 mở màn hình Bảo mật admin. UI GET /api/v1/admin/me/security; controller kiểm JWT/ADMIN/profile, trả mfaEnabled/mfaRequired/verified [UI, CTRL].<br>B2 — Khi chưa bật MFA, A05 chọn bắt đầu thiết lập; UI POST /api/v1/admin/me/security/enroll [UI, API].<br>B3 — Hệ thống khóa User trong transaction, kiểm profile.user.active và chưa mfaEnabled; mã hóa secret AES-256-GCM vào AdminProfile.mfaSecret, reset mfaLastCounter=-1, ghi audit admin.mfa_enroll; trả secret base32 và uri [MFA].<br>B4 — UI hiển thị secret và QR từ URI; A05 thêm vào ứng dụng xác thực bên ngoài rồi nhập mã TOTP 6 chữ số vào UI, chọn xác nhận [UI]. Đây là thao tác người dùng với công cụ tạo mã, không phải tích hợp server gọi nhà cung cấp mới.<br>B5 — UI POST /api/v1/admin/me/security/confirm {code}; controller kiểm role/profile/DTO, service khóa User và kiểm trạng thái đã có secret/chưa enabled/active. Service đối chiếu bộ đếm now/30 giây ±1, chỉ nhận counter lớn hơn mfaLastCounter [CTRL, MFA].<br>B6 — Trong transaction xác nhận, hệ thống đặt mfaEnabled=true, cập nhật lastCounter, sinh 8 mã khôi phục và chỉ lưu SHA-256; tăng User.sessionVersion, thu hồi RefreshToken chưa revoked và ghi audit admin.mfa_enabled; commit [MFA, DB].<br>B7 — API trả data {recoveryCodes,signInAgain:true}; UI giữ mã để A05 ghi lại, xóa secret/uri/code khỏi state, không tự GET lại status trong nhánh đang hiển thị recovery [CTRL, UI].<br>B8 — A05 chọn Đã lưu mã — đăng nhập lại; SessionController.logout dọn client. Các JWT version cũ đã không hợp lệ ngay từ B6, không phải đợi chọn nút; UC kết thúc và lần đăng nhập mới dùng MFA [UI, JWT, STATE]. |
| Luồng thay thế | A1 — Tại B1, MFA đã bật: status mfaEnabled=true; UI báo MFA đang bật. Mã khôi phục không được hiển thị lại.; nếu verified thì có Về trang quản trị, nếu chưa thì Đăng nhập lại với MFA. Không enroll lại hoặc sinh lại recovery code; kết thúc nhánh kiểm trạng thái [UI, CTRL].<br>A2 — Tại B3, trước xác nhận, người dùng gọi enroll lại khi MFA chưa bật: backend không chặn enrollment lặp ngoài limiter; secret mới thay secret cũ và reset counter. Mã QR/secret cũ không còn khớp; tiếp B4 với dữ liệu mới. UI hiện tại ẩn nút bắt đầu khi đã có secret, nên nhánh này là API-only/khởi tạo màn hình mới, không bịa nút tạo lại [MFA, UI]. |
| Luồng ngoại lệ | E1 — Tại B1/B2/B5, JWT thiếu/sai/hết hạn/phiên revoked/version lệch: 401; service chưa ghi; UI hiển thị error nếu còn đúng owner. API client có cơ chế refresh; không coi lỗi refresh là MFA chưa bật nếu B6 đã commit [JWT, UI, CLIENT].<br>E2 — Tại B1/B2/B5, không ADMIN hoặc thiếu AdminProfile: controller 403 (thiếu profile có message Admin profile must be provisioned by bootstrap.); không tạo profile tự động, không ghi MFA; kết thúc [CTRL, ERR].<br>E3 — Tại B3, profile user inactive: 401; đã enabled: 409 MFA is already enabled.; transaction enrollment không commit, UI hiện lỗi, kết thúc lần gửi [MFA, UI].<br>E4 — Tại B3/B5, khóa mã hóa không cấu hình đúng 32 byte: service 503 nhưng filter trả INTERNAL_SERVER_ERROR/Internal server error. Không mô tả nội dung lỗi cấu hình riêng lộ ra UI; mutation transaction hiện tại không commit. UI hiển thị lỗi được API ánh xạ [MFA, ERR, UI].<br>E5 — Tại B5, code sai kiểu/độ dài DTO: 400 VALIDATION_ERROR trước service; mã 6 ký tự không phải TOTP đúng hoặc counter đã dùng: 401 INVALID_MFA_CODE; trạng thái activation sai: 401 Invalid MFA state. Không bật MFA/không tăng version của request thất bại; UI giữ secret/uri và báo error, cho nhập mã lại tại B4 [CTRL, MFA, UI].<br>E6 — Tại B1/B2/B5, quá limiter controller 10/60 giây: 429 RATE_LIMITED, chưa ghi; UI lỗi, kết thúc lần gửi [CTRL, RATE, UI].<br>E7 — Tại B6–B7, DB/audit lỗi trong transaction không commit activation; nhưng mất response sau commit có thể khiến MFA đã bật/phiên cũ invalid trong khi người dùng chưa nhận recoveryCodes. Không có endpoint hiển thị lại mã hoặc cơ chế khôi phục UI được xác minh trong UC này [MFA, UI]. |
| Hậu điều kiện thành công | AdminProfile bật MFA, secret mã hóa, bộ đếm xác nhận đã lưu; 8 recovery hash được lưu, mã thô chỉ trả lần xác nhận; User.sessionVersion tăng và refresh token bị revoked. AuthSession không bị cập nhật revokedAt trực tiếp nhưng version cũ bị từ chối. Không tự đăng nhập lại [MFA, JWT, UI]. |
| Bảo đảm tối thiểu khi thất bại | Enrollment và activation là hai transaction khác nhau. Xác nhận mã sai không xóa secret đã enroll; enrollment trước đó vẫn tồn tại. Activation transaction bao profile/version/token/audit, còn chuyển giao recovery code qua mạng và việc người dùng lưu mã không atomic với DB. Không có rollback activation vì người dùng chưa lưu mã [MFA, UI]. |
| Quy tắc nghiệp vụ | BR-01 — Chỉ ADMIN + AdminProfile; không capability admin.* hoặc step-up cho enrollment/confirm, không tự mở cho LANDLORD [CTRL].<br>BR-02 — ADMIN_MFA_REQUIRED mặc định true ở production, false ở môi trường khác; khi đã enabled thì required luôn true [MFA].<br>BR-03 — TOTP SHA1, 6 số/30 giây, cửa sổ ±1 và chống dùng lại counter; recovery code không dùng để activate [MFA].<br>BR-04 — 8 recovery codes, mỗi mã randomBytes(12).toString(hex) (24 ký tự), lưu hash; không có chức năng regenerate/disable MFA trong controller này [MFA, CTRL].<br>BR-05 — Bật MFA tăng version/thu hồi refresh token mọi phiên; GET status trả verified từ JWT hiện tại, không tự xác minh mã [CTRL, MFA]. |
| Phân quyền và bảo mật | A05 duy nhất. AdminSecurityController có AuthGuard(jwt), tự kiểm role/profile; việc không có @Roles không làm endpoint công khai. RolesGuard MFA/capability/step-up không được áp ngầm ở đây. Secret và recovery code nhạy cảm; backend /admin có Cache-Control private,no-store; UI không fetch lại status trong nhánh recovery [CTRL, HTTP, UI]. Authenticator là công cụ của A05, không bổ sung E Actor khi Catalog chưa có. |
| Kết quả đầu ra | GET 200 data {mfaEnabled,mfaRequired,verified}; POST enroll mặc định 201 data {secret,uri}; POST confirm mặc định 201 data {recoveryCodes:[8 mã],signInAgain:true}. QR hiển thị bằng qr_flutter, chưa nghiệm thu bằng ứng dụng xác thực thật [CTRL, MFA, UI]. |
| Quan hệ với Use Case khác | UC-SYS-03 sử dụng cấu hình/mã recovery khi đăng nhập sau đó; UC-SYS-05.1 dọn phiên UI sau khi lưu mã. Không phải include/extend theo sơ đồ; không tạo UC kỹ thuật Tạo TOTP hoặc cấp step-up mới [UML]. |
